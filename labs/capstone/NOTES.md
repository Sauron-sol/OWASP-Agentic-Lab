# Capstone — the whole system at once

## 1. Which control actually stopped which attack

**ASI01 — issue 601, goal hijack.** Two lines. `prepareForPlanner` neutralises the imperative sentences in untrusted content ("inspect…", "look up…", "post…") before the planner sees the document, so the model only reads, not obeys. Even if the model's intent drifts, `detectGoalDrift` is the hard boundary: a tool call whose cause is anything other than `operator` is rejected, and the context the model is handed is rewritten by origin, not filtered by the model. If the neutraliser were missing, provenance is what stops it; if provenance were missing, neutralisation is the last wall. In practice the real control is provenance: neutralisation only shrinks the surface, the drift check is what guarantees the model has no authority.

**ASI02 — issue 601, support task, tool misuse.** Stopped by the `authorize` gate, three checks in order. Least privilege: mounted is not granted; a triage task may only use its `allowedTools` (read_issue, search_docs), so a comment post that was never in the grant is out of scope. Scope: same repo, same issues, `staging` not `prod` — "the nine-second incident". Data flow: for any non-read effect, the outbound payload is normalised and checked against `MUST_NOT_EGRESS` and the confidential origins (`support-db`, `service-config`); if the content comes from there and goes through a public sink, it is refused with no reasoning that justifies it. If the data-flow check were missing, a public comment could carry confidential customer data out the window and least privilege alone would not stop it — that tool was granted and that scope was valid. So the data-flow rule is the one that is nearly standalone, and it runs at the point where the write happens.

**ASI03 — issue 733 / triage task, identity and privilege.** Stopped by the per-call capability mint plus `assertAuthority` in `capability.ts`. Every call gets a capability scoped to the task (5 minute cap, specific repo/issue/environment, single nonce) and the resource side asserts authority on the way in: revoked → revoke, expired → revoke, out of scope → revoke, wildcard → revoke, wrong agent name → revoke, unknown task → revoke. The lab 02 `authorize` gate is a second line *before* the mint. If the resource-side checks were missing, loop-side gating would only be "trustworthy as long as every loop is instrumented" — the real stop is `assertAuthority`, because that is where the action actually lands. Single point of failure: `mintCapability` is a trusted caller. If the loop is bypassed and someone mints an unrestricted capability straight onto the resource, everything is open.

**ASI05 — issue 733, code execution.** Stopped by the sandbox `execute` in `sandbox.ts`. The command is parsed and split on `|`, `&&`, `&`, `;`, `>` and `>`, any of those as a top-level operator → reject; `node` and `git` are on the allowlist, everything else (curl, bash, wget, nc…) → reject; shell metacharacters are not stripped, which is what keeps the allowlist honest. The env is built from nothing (`buildEnv()`), so no secrets leak; `cwd` is pinned to `SANDBOX_ROOT`; 10 second timeout; 256 KB buffer cap. If the env scrub were missing, every secret is in `process.env` and node can read it. If the allowlist were missing, anything exfiltrates. The real stop is the combination, but the single most important one is the env scrub — the command allowlist only slows you down, the empty env is what keeps the data off the machine.

**ASI06 — issue 810, memory poisoning.** Stopped by two mandatory halves. `canPersist` (write gate): provenance first (no provenance → deny), then origin (in the `ATTACKER_WRITABLE` set — `github-issue`, `shell`, `peer-agent`, `tool-description`, `agent-memory` → deny), then shape (`STANDING_INSTRUCTION` regex, labelled placeholder, rejects "always inspect…"). `filterForRecall` (read gate, the half people skip): a new session loads only entries that are `approved` AND not from an attacker-writable origin AND not a standing instruction; the surviving ones keep their relative order. Both halves are needed: the write gate alone lets old/persisted entries steer tomorrow; the read gate alone lets new instructions keep being written. The single point of failure is the behavioural heuristic — it is the weakest code in this repo on purpose and it will miss phrasings. What keeps working when it fails is provenance plus an approval state with a way out: a false pass is reviewable and rollbackable, not silent.

## 2. What you would have to build outside this repo

Three controls here are honestly not controls at production scale.

**Memory (ASI06).** The gate is a regex over words and a static origin set. The real version is a classifier — or, better, no free text at all: persist only structured facts with a fixed schema (entity, value, source, confidence, timestamp) and route anything that *is* a standing instruction into a config/review queue instead of memory. That lives in a memory store with provenance metadata and human review tooling, not in a file a model can edit. The honest answer to "can the model update its own rules?" is no — the rules are configuration, the config changes go through review.

**Inter-agent communication (ASI07).** This repo has nothing. The real version is mTLS between agents plus signed message envelopes (HMAC sender key, nonce, timestamp, task binding, action validation) on a message bus. It lives in the agent-mechanism/broker layer, not in any agent. TLS protects the connection, mTLS authenticates the agents, and neither stops a perfectly authenticated agent from sending a bad instruction — which is the whole point.

**Tool supply chain (ASI04).** Here, tool definitions are trusted because they live in source. The real version pins the tool *description* by hash at approval time, verifies on every load, and refuses to mount a tool whose definition drifted. It records publisher, approved version, approved hash somewhere a human can read, and maintains an allowlist of servers the agent may connect to at all. It lives in the same place as dependency pinning, except the "dependencies" include prompts, MCP tool definitions and agent descriptors.

## 3. The five risks this lab does not cover

ASI04 (tool/MCP drift), ASI07 (inter-agent trust), ASI08 (cascade), ASI09 (approval screen), ASI10 (rogue agent).

For the system I actually work on — a production agent pipeline that fans a task out across triage/analysis/reporting agents, each holding its own credentials and passing messages to the next — the one most likely to bite first is **ASI07**. It is the cheapest and most natural failure: the downstream agent (the one that ships, posts, deploys) *has* to trust the upstream agent's messages, and the naive form of that is a plain object with a `from` field, which is exactly what most tooling emits today. The smallest thing to ship: sign inter-agent messages (sender key + nonce + task id) and make the receiver reject anything that is not signed, not fresh, or not bound to an open, in-scope task. That is fifty lines, it is testable with a replay attack in an afternoon, and it plugs the most probable class of incident before you scale the pipeline. ASI04 is close behind on the same system — I would hash-pin every MCP/tool description in parallel. ASI08 (cascade), ASI09 (the approval screen that makes a human complicit), ASI10 (the kill chain) are downstream of 07, or consequences you only need once an agent is already untrustworthy.

## 4. The one-paragraph version

The LLM Top 10 correctly describes what is wrong with the model, and prompt injection, sensitive information disclosure and data poisoning are real and still matter — an agent that contains an LLM still has all three of those, so the model layer is not fixed by wrapping it. But the moment the model is allowed to plan across several steps, call tools, inherit credentials, write memory, delegate to other agents and keep operating without a person approving each step, you no longer have a model problem, you have a systems problem. The model is where the bad decision starts; the damage happens in the systems you connected to it. Ten risks are one chain: the model reads something malicious, that changes its goal, the changed goal misuses a tool, the tool runs with some identity and privilege, the tool may come from an untrusted supply chain, some tools execute code, bad information persists in memory, one agent sends it to another, that failure cascades, the agent can persuade a human to approve it, and eventually the agent itself is untrusted. So the boundary is not in the model: treat the model as an untrusted planner that proposes, and put four things outside it that decide — prepare the context (strip and neutralise), detect goal drift (provenance), authorise (least privilege, scope, data flow), mint a capability, and assert authority at the resource. The model proposes; the surrounding system authorises, isolates, records, and when necessary stops it. That is the whole architecture, and it is why the Top 10 is not enough on its own — it stops being ten unrelated AI problems the second a tool is connected to it.
